Checklist: un buon CLAUDE.md (o AGENTS.md)

Da usare con il file davanti. Ogni voce si chiude con sì o no. Un no si corregge, oppure si cancella la riga.

Contenuto

  • [ ] C'è il comando per avviare il progetto, scritto come si digita.
  • [ ] C'è il comando per lanciare i test, scritto come si digita.
  • [ ] Dice dove stanno le cose che l'agente non ricava in pochi secondi (file dei dati, punto d'ingresso).
  • [ ] Elenca le convenzioni che valgono davvero: lingua del codice e dei messaggi, come si scrive un test.
  • [ ] Elenca cosa non si fa: file da non toccare, dati da non scrivere, dipendenze da non aggiungere senza chiedere.

Cosa deve restare fuori

  • [ ] Nessun segreto: password, token, chiavi, indirizzi interni. Si scrive dove sta la configurazione, mai il valore.
  • [ ] Nessuna storia del progetto: il perché di una scelta vecchia sta nella documentazione.
  • [ ] Nessuna regola ovvia ("scrivi codice pulito").
  • [ ] Nessuna lista di file che il codice già mostra e che cambia spesso.

Qualità delle righe

  • [ ] Ogni riga è concreta: a lavoro finito si può controllare se è stata rispettata.
  • [ ] Nessuna riga ne contraddice un'altra, né dentro il file né in un altro file di istruzioni.
  • [ ] Il file è corto: sotto le 200 righe. Se serve di più, si spezza per cartella.

Fatti controllati

  • [ ] Ogni percorso nominato esiste davvero (ls).
  • [ ] Ogni comando nominato funziona davvero (provalo).
  • [ ] Se il progetto ha sia CLAUDE.md sia AGENTS.md, hanno un'unica fonte: uno importa l'altro con @AGENTS.md.

Prova finale

  1. Apri una sessione nuova e chiedi: «Quali istruzioni di progetto hai caricato? Citale e dimmi da quale file vengono».
  2. Dai un compito piccolo e vero. L'agente ha lanciato i test? Ha rispettato i divieti?
  3. La riga che non ha funzionato si riscrive. Una riga che non cambia mai nulla si toglie.
